## 2. 数据表设计

### 2.1 users (用户表)

| 字段名 | 类型 | 长度 | 允许NULL | 默认值 | 说明 |
|--------|------|------|---------|--------|------|
| id | BIGINT | - | NO | AUTO_INCREMENT | 主键ID |
| email | VARCHAR | 255 | NO | - | 邮箱地址 (唯一) |
| password | VARCHAR | 255 | NO | - | 加密密码 (bcrypt) |
| name | VARCHAR | 100 | NO | - | 用户姓名 |
| avatar | VARCHAR | 500 | YES | NULL | 头像URL |
| reset_token | VARCHAR | 255 | YES | NULL | 密码重置Token |
| reset_token_expires | DATETIME | - | YES | NULL | 重置Token过期时间 |
| created_at | DATETIME | - | NO | CURRENT_TIMESTAMP | 创建时间 |
| updated_at | DATETIME | - | NO | CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP | 更新时间 |
| deleted_at | DATETIME | - | YES | NULL | 删除时间 (NULL=未删除) |

**索引**:
- PRIMARY KEY: `id`
- UNIQUE KEY: `idx_email` (`email`)

**DDL**:
```sql
CREATE TABLE users (
  id BIGINT NOT NULL AUTO_INCREMENT,
  email VARCHAR(255) NOT NULL,
  password VARCHAR(255) NOT NULL,
  name VARCHAR(100) NOT NULL,
  avatar VARCHAR(500) NULL,
  reset_token VARCHAR(255) NULL DEFAULT NULL,
  reset_token_expires DATETIME NULL DEFAULT NULL,
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  deleted_at DATETIME NULL DEFAULT NULL,
  PRIMARY KEY (id),
  UNIQUE KEY idx_email (email),
  INDEX idx_deleted (deleted_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
```

### 2.3.1 reminders (提醒通知表)

记录用户设置的提醒通知，支持时间块级别和便签级别提醒。

**设计说明**: 用户可以为某个时间块设置提前提醒，在指定时间收到通知。

| 字段名 | 类型 | 长度 | 允许NULL | 默认值 | 说明 |
|--------|------|------|---------|--------|------|
| id | BIGINT | - | NO | AUTO_INCREMENT | 主键ID |
| user_id | BIGINT | - | NO | - | 所属用户ID |
| target_type | VARCHAR | 20 | NO | 'time_block' | 提醒目标类型: time_block/note |
| target_id | BIGINT | - | NO | - | 目标ID（时间块ID或便签ID） |
| remind_at | DATETIME | - | NO | - | 提醒触发时间 |
| advance_minutes | INT | - | NO | 0 | 提前提醒分钟数 |
| is_auto | TINYINT | 1 | NO | 0 | 是否自动生成 |
| note_id | BIGINT | - | YES | NULL | 关联便签ID（自动提醒时记录） |
| title | VARCHAR | 200 | NO | - | 提醒标题 |
| message | TEXT | - | YES | NULL | 提醒消息内容 |
| status | VARCHAR | 20 | NO | 'pending' | 状态: pending/triggered/dismissed/cancelled |
| triggered_at | DATETIME | - | YES | NULL | 触发时间 |
| dismissed_at | DATETIME | - | YES | NULL | 关闭时间 |
| created_at | DATETIME | - | NO | CURRENT_TIMESTAMP | 创建时间 |
| updated_at | DATETIME | - | NO | CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP | 更新时间 |

**索引**:
- PRIMARY KEY: `id`
- INDEX: `idx_reminder_user` (`user_id`)
- INDEX: `idx_reminder_target` (`target_type`, `target_id`)
- INDEX: `idx_reminder_status` (`user_id`, `status`, `remind_at`) — 定时查询待触发提醒

**外键**:
- FOREIGN KEY (`user_id`) REFERENCES `users`(`id`) ON DELETE CASCADE
- FOREIGN KEY (`note_id`) REFERENCES `notes`(`id`) ON DELETE SET NULL
- 注意：`target_id` 为 polymorphic 字段（可指向 time_blocks 或 notes），不创建外键约束

**DDL**:
```sql
CREATE TABLE reminders (
  id BIGINT NOT NULL AUTO_INCREMENT,
  user_id BIGINT NOT NULL,
  target_type VARCHAR(20) NOT NULL DEFAULT 'time_block',
  target_id BIGINT NOT NULL,
  remind_at DATETIME NOT NULL,
  advance_minutes INT NOT NULL DEFAULT 0,
  is_auto TINYINT(1) NOT NULL DEFAULT 0,
  note_id BIGINT NULL DEFAULT NULL,
  title VARCHAR(200) NOT NULL,
  message TEXT NULL,
  status VARCHAR(20) NOT NULL DEFAULT 'pending',
  triggered_at DATETIME NULL,
  dismissed_at DATETIME NULL,
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (id),
  INDEX idx_reminder_user (user_id),
  INDEX idx_reminder_target (target_type, target_id),
  INDEX idx_reminder_status (user_id, status, remind_at),
  INDEX idx_reminder_note (note_id),
  INDEX idx_reminder_auto (is_auto),
  CONSTRAINT fk_reminder_user FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE,
  CONSTRAINT fk_reminder_note FOREIGN KEY (note_id) REFERENCES notes(id) ON DELETE SET NULL
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='提醒通知表';
```

**使用流程**:

```
用户创建时间块时勾选"开启提醒"
  → 计算 remind_at = start_time - advance_minutes
  → INSERT INTO reminders (user_id, target_type='time_block', target_id, remind_at, advance_minutes, title, message)

前端定时检查（每分钟）
  → SELECT * FROM reminders WHERE user_id = ? AND status = 'pending' AND remind_at <= NOW()
  → 发送浏览器通知 + 播放音效
  → UPDATE reminders SET status = 'triggered', triggered_at = NOW()

用户点击"关闭提醒"
  → UPDATE reminders SET status = 'dismissed', dismissed_at = NOW()

用户删除时间块
  → UPDATE reminders SET status = 'cancelled' WHERE target_type = 'time_block' AND target_id = ?
```

## 4. 关键设计策略

### 4.1 时区处理策略

**策略**: 统一使用 `TIMESTAMP` 类型存储 UTC 时间，应用层负责时区转换。

| 层级 | 处理方式 |
|------|---------|
| **数据库存储** | `start_time` / `end_time` 使用 `TIMESTAMP`，自动转为 UTC 存储 |
| **后端 API** | 返回 ISO 8601 格式（带 Z 后缀），如 `2024-01-01T09:00:00Z` |
| **前端展示** | 根据用户本地时区自动转换显示（如 `2024/1/1 17:00 北京时间`）|
| **Electron 桌面端** | 使用 `Intl.DateTimeFormat` 或 day.js 按系统时区渲染 |

**原因**: 用户可能在不同时区的设备上使用（如出差、跨國），UTC 存储确保数据一致性。

### 4.2 软删除策略

**策略**: 核心业务表（users、notes、time_blocks）使用 `deleted_at` 字段实现逻辑删除。

| 操作 | 实现方式 |
|------|---------|
| **删除** | `UPDATE ... SET deleted_at = NOW() WHERE id = ?` （而非 DELETE） |
| **查询** | 所有 SELECT 默认加 `WHERE deleted_at IS NULL` 条件 |
| **恢复** | `UPDATE ... SET deleted_at = NULL WHERE id = ?` |
| **物理清理** | 定期任务清理 `deleted_at` 超过 30 天的记录（可配置） |

**原因**:
- 防止用户误操作导致数据永久丢失
- 数据同步时可正确识别"被删除"与"不存在"两种状态
- 支持数据恢复功能

## 5. 数据库优化建议

### 5.1 索引优化
- `time_blocks`表的`start_time`和`end_time`字段经常一起查询，已创建联合索引
- 按用户分区查询，所有索引都包含`user_id`作为前缀

### 5.2 分区策略
- 对于大数据量，可以考虑按时间对`time_blocks`表进行分区
- 按`user_id`进行分库分表（当用户量达到百万级时）

### 5.3 数据归档
- 定期归档一年前的历史数据到归档表
- 归档数据只保留统计分析所需的基本信息

### 5.4 查询优化
- 使用覆盖索引减少回表
- 对于复杂统计查询，考虑使用物化视图或预计算
- 适当使用Redis缓存热点数据

## 7. 变更记录

### 7.1 P0 性能优化变更

#### 变更 1：修正 `note_id` 索引为联合索引

| 项目 | 修改前 | 修改后 |
|------|--------|--------|
| 索引名 | `idx_note_id (note_id)` | `idx_user_note (user_id, note_id)` |
| 影响表 | time_blocks | time_blocks |

**修改原因**：

原索引 `(note_id)` 是单列索引。当执行"查看某便签下所有时间块"的查询时：
```sql
-- 如果只按 note_id 查询，没有 user_id 过滤
SELECT * FROM time_blocks WHERE note_id = 5;
```
MySQL 会扫描**所有用户**的该便签数据，在多租户场景下这是严重的性能问题和安全漏洞（跨用户数据泄露风险）。

实际业务中，所有查询必然带 `user_id` 条件，因此将 `user_id` 作为前缀列，既能利用 B+Tree 的最左前缀原则精确定位到该用户的该便签数据，又天然实现了租户隔离。

---

#### 变更 2：新增日视图覆盖索引

| 项目 | 内容 |
|------|------|
| 新增索引 | `idx_user_date_covering (user_id, deleted_at, start_time, end_time, note_id, title, is_completed)` |
| 类型 | 覆盖索引（Covering Index） |
| 影响表 | time_blocks |

**修改原因**：

日视图是**最高频的查询场景**——用户每次打开应用都会触发。原始 SQL 如下：

```sql
SELECT id, title, note_id, start_time, end_time, is_completed
FROM time_blocks
WHERE user_id = ? AND deleted_at IS NULL
  AND start_time < '当天结束' AND end_time > '当天开始'
ORDER BY start_time;
```

原有索引 `idx_time_range(user_id, start_time, end_time)` 存在两个问题：

1. **缺少 `deleted_at` 列**：软删除策略要求所有查询都加 `deleted_at IS NULL`，但原索引不包含此列，导致 MySQL 需要回表过滤，大量已删除行仍被扫描。
2. **非覆盖索引**：日视图只需要 id、title、note_id、start_time、end_time、is_completed 这几个字段。原索引不包含这些数据列，每次命中索引后还需要回表（随机 I/O）读取完整行数据。

覆盖索引将这些字段全部包含在索引 B+Tree 的叶子节点中，使得日视图查询可以**完全通过索引完成，零回表**。

**性能对比预估**（单用户 5000 条时间块）：

| 指标 | 修改前 | 修改后 |
|------|--------|--------|
| 扫描行数 | ~2000 行（含已删除） | ~50 行（精确匹配） |
| 回表次数 | ~50 次（每条命中的行） | **0 次** |
| 响应时间 | ~25-40ms | **~2-5ms** |
| I/O 类型 | 随机 I/O（回表） + 顺序 I/O（索引扫描） | 纯顺序 I/O（索引扫描） |

**空间代价**：覆盖索引会增加约 15-20% 的索引存储空间。对于 time_blocks 表（预计单用户 <10000 条），额外占用 <5MB，完全可接受。

#### 变更 3：新增全文搜索索引

| 项目 | 内容 |
|------|------|
| 新增索引 | `FULLTEXT INDEX ft_title_desc (title, description)` |
| 类型 | MySQL 全文索引（FULLTEXT） |
| 影响表 | time_blocks |

**修改原因**：

搜索功能使用 `LIKE '%关键词%'` 进行模糊匹配时，存在致命的性能问题：

```sql
-- 原始搜索方式（极慢）
SELECT * FROM time_blocks
WHERE user_id = ? AND deleted_at IS NULL
  AND (title LIKE '%需求%' OR description LIKE '%需求%');
```

`LIKE '%xxx%'` 的通配符在开头，**无法使用任何 B+Tree 索引**，MySQL 必须对符合条件的每一行做全表扫描 + 字符串逐字比对。当数据量增长后：

| 数据量 | LIKE '%xxx%' 响应时间 | FULLTEXT 响应时间 |
|--------|----------------------|-------------------|
| 1,000 条 | ~80ms | ~3ms |
| 10,000 条 | ~800ms+ | ~8ms |
| 50,000 条 | >4 秒（不可接受） | ~25ms |

MySQL FULLTEXT 索引基于**倒排索引**（Inverted Index）实现，对中文分词（需要 MySQL 配置 `ngram parser`）有良好支持。查询语法从 `LIKE` 改为 `MATCH...AGAINST`：

```sql
-- 优化后的搜索方式
SELECT * FROM time_blocks
WHERE user_id = ? AND deleted_at IS NULL
  AND MATCH(title, description) AGAINST('需求' IN NATURAL LANGUAGE MODE)
ORDER BY start_time DESC
LIMIT 20;
```

**注意事项**：
- 全文索引对 DML 操作（INSERT/UPDATE/DELETE）有少量写入开销（维护倒排索引）
- 对于 TEXT 类型的 `description` 字段，全文索引比 LIKE 扫描效率高数个数量级
- MySQL 全文索引默认最小词长度为 3（`ft_min_word_len=2` 建议设为 2 以支持中文双字词）

### 7.2 提醒通知功能 — 新增 reminders 表

#### 设计背景

用户在规划时间块时，常常需要在某个时间点收到提醒通知。例如：
- "会议将在10分钟后开始"
- "该休息了"

#### 设计要点

1. **target_type/target_id**：支持时间块级别提醒和便签级别提醒
2. **advance_minutes**：提前提醒分钟数（如提前5分钟提醒）
3. **status**：pending（待触发）、triggered（已触发）、dismissed（已关闭）、cancelled（已取消）
4. **定时检查**：前端每分钟检查待触发的提醒，发送浏览器通知

#### 对现有表的影响

| 表 | 是否需要修改 | 说明 |
|----|-------------|------|
| time_blocks | 不需要修改 | reminders 通过 target_id 外键关联 |
| users | 不需要修改 | 通过 user_id 外键关联 |
| notes | 不需要修改 | 可设置便签级别提醒 |
